# cfdb-extractor-php

PHP `LanguageProducer` MVP (RFC-041 Phase 2 / issue #264). Walks a Composer-style PHP project via tree-sitter-php and emits the v0.1 cfdb fact set onto the existing closed-set schema vocabulary in `cfdb-core::schema::labels` — no new `:Item.kind` values are introduced (Published Language invariant per RFC-041 §4). Operationally a cfdb-monolith member crate per `.cfdb/concepts/cfdb.toml`; gated behind `lang-php` in `cfdb-cli` so default builds drop the entire tree-sitter dep tree.

## PhpProducer

Reference implementation of `cfdb_lang::LanguageProducer` for PHP workspaces. `name()` returns `"php"` (matching the `lang-php` Cargo feature on `cfdb-cli`). `detect()` is the marker-file check `workspace_root.join("composer.json").is_file()` — Composer's PSR-4 manifest is the canonical PHP project marker. `produce()` walks the `.php` files under the roots `composer.json` declares across `autoload` and `autoload-dev` — psr-4, psr-0, classmap, files, exclude-from-classmap — so a workspace declaring no root walks nothing and a built project's generated `var/` is never read as source (issue #687); a workspace with no manifest at all is refused as `LanguageError::NotDetected` naming this producer, since `detect()` requires the file (issue #688). It parses each file via tree-sitter-php's `LANGUAGE_PHP` constant (0.23 ABI shared with `cfdb-extractor-ts`), and emits sorted-canonical `(Vec<Node>, Vec<Edge>)`. Any tree-sitter parse failure or I/O error wraps to `LanguageError::Parse { producer: "php", ... }` / `LanguageError::Io`. Schema mapping decision (preserves the closed-set invariant; documented in the crate-root doc + `Cargo.toml` header): PHP `namespace` → `:Module` node; PHP `class` / `interface` / `trait` → `:Item { kind: "trait", php_construct: <ast-kind> }` and PHP `enum` → `:Item { kind: "enum", php_construct: "enum_declaration" }` (the `php_construct` prop is the disambiguation seam for cypher queries that need to distinguish them; `"enum"` is already inside `cfdb-041-language-backend-trait#4`'s closed kind set, so no kind, no label and no schema version is added — `cfdb-045-polyglot-relationship-edges#3.2`, amended 2026-09-07); PHP `method` / `function` → `:Item { kind: "fn" }`, a method declared in an enum body carrying the enclosing enum's qname exactly as a class method does (`cfdb-045-polyglot-relationship-edges#2`, `#3.4` D4); PHP `const` → `:Item { kind: "const" }` (reserved; MVP doesn't yet emit class constants). Defined at `crates/cfdb-extractor-php/src/lib.rs:75`.

Name resolution precedes D2. The target of an `implements` clause is resolved the way PHP resolves a name: a fully qualified name stands as written; an unqualified or qualified name goes first through the file's `use` imports — plain, aliased (`use A\B as C`) and grouped (`use A\{B, C}`) — and otherwise through the current namespace; only the resolved qualified name is matched against the in-workspace item set, and an `IMPLEMENTS` edge exists iff that match succeeds (cfdb-045 §3.2, D2). The callee of a scoped call resolves through the same table before the `CALLS` decision of cfdb-045 §3.4. An `implements` clause on an enum is read as one on a class is, keyed on the clause and not on what declares it (cfdb-045 §3.2, 45-A). A name that resolves outside the workspace yields no edge and no placeholder, as D2 orders; a name resolved to the current namespace when a `use` import names it is a producer defect, never a closed-world case.

Every walked file is a `:File` node carrying `path` and `crate` (`php-workspace`, the single synthetic crate), its id built by `cfdb_core::qname::file_node_id` — the same constructor the Rust walker calls, so the formula lives in one place (cfdb-060-php-fact-model#3.1.1). It carries no `IN_CRATE` edge, because the Rust `:File` carries none and a PHP-only edge would make `MATCH (f:File)-[:IN_CRATE]->(:Crate)` silently answer for PHP alone, and no `IN_MODULE`, because a PHP file may open several namespaces and file-to-module is then not a function. Neither `loc` nor `module_qpath` is emitted: no producer emits them, and an attribute emitted empty is worse than one absent.

Each class-importing `use` clause is one `:Import` node, hung off its declaring `:File` by a `HAS_IMPORT` edge (cfdb-060-php-fact-model#3.1.2). The node carries the `fqn` with the group prefix joined and any leading backslash trimmed, the `alias` exactly as written when the clause has one, the declaring `file` denormalized, and the `line`. The id `import:{file}:{fqn}:{idx}` carries a per-FQN ordinal because two clauses in one file may import the same name — `use A\B\C;` beside `use A\B\C as D;` — and last-write-wins ingest would drop one of them in silence that no identity-contention warning can see, the collision being same-file by construction. The FQN is recorded whether or not a node with that name exists: the framework names a consumer's architecture rules hunt live in `vendor/`, outside every declared root, so a model recording only resolved targets would record nothing those rules ask for. `:Import` is not the producer's internal alias table, which is case-folded and last-write-wins by design; the node is the lossless record of a declaration. A `use` clause nested inside a braced `namespace A { ... }` body yields no `:Import`: the import walk reads direct children of the program node, the same reach that already misses classes declared in such a body.

A `new X(...)` is a `:CallSite` carrying `kind` `"new"`, the fourth member of that closed set beside `call`, `fn_ptr` and `serde_default` (cfdb-060-php-fact-model#3.2). `callee_path` holds the class name exactly as the source writes it — `\DateTimeImmutable`, `DateTimeImmutable`, `self` — so a rule reads what a developer would grep for, and `resolve_target` is that name resolved through the file's imports with `::__construct` appended, because a construction calls a constructor. When the class is in the walked tree and declares one, `callee_resolved` is true and a `CALLS` edge lands on the constructor item; when it declares none, or lives outside every declared root, the site stands alone. `new self()` and `new static()` parse as a plain `name` and route through the same relative-scope resolution a scoped call uses, reaching the enclosing class's constructor rather than the namespaced `App\…\self` that qualifying the keyword would produce; `new parent()` is unresolved. A construction whose class position is not a `name` or `qualified_name` — `new class { }`, `new $cls()`, `new ($f->t())()` and the member, subscript and scoped-property forms — emits no construction fact, the same silence every unhandled shape already receives; a call expression nested inside such a position is unaffected and stays the call site it always was.

Every argument of every call site this producer emits is an `:Argument` node hung off it by `HAS_ARG` (cfdb-060-php-fact-model#3.3, #3.4), including the arguments of a construction. The unit is the grammar's `argument` wrapper rather than the expression it holds, so `source_text` is the wrapper's byte range and carries a named argument's `name:`, a spread's `...` and a by-reference `&`. Position 0 is the receiver on a `member_call_expression` or its nullsafe form and the first written argument everywhere else, which is `RECEIVER_POSITION`'s meaning in every producer. `kind` is the closed set `cfdb_core::schema::ARG_KINDS`, classified from the wrapper: a `reference_modifier` field makes it `ref`, otherwise the wrapper's value child is classified, descending through a `variadic_unpacking` first. A `variadic_placeholder` — the first-class-callable `f(...)` — is not wrapped in an `argument` and yields no fact, so a following argument keeps position 0. Every attribute is read while the tree and the source buffer are alive and carried owned on the pending call site, because `walk_file` drops both before the call sites resolve.

An enum's cases yield no `:Item`. No clause admits a PHP variant — neither `cfdb-045-polyglot-relationship-edges` nor `cfdb-041-language-backend-trait` carries one, and the `:Variant` label is the Rust producer's — and `cfdb-041-language-backend-trait#4.5` gates the widening behind its own RFC. The silence is declared here rather than left to be read off an empty result: a rule reaching for a case's name finds nothing because nothing is emitted, not because the walk failed.
