## Per-RFC analysis

### RFC-047 — impact / blast-radius

**Position: the layering is correct; the composition target is fictional.** The RFC's clean-arch claim (§3.1) — `impact` is a `cfdb-cli` dispatch branch composing the existing `query` port, zero new `cfdb-core` logic — is exactly right and matches the shipped precedent: `commands/query.rs:120 list_callers` already does this (loads an embedded `.cypher` template, binds a `$qname` param via `parsed.params.insert(...)`, calls `store.execute(&ks, &parsed)`). `impact` slots into `dispatch_typed` (`commands.rs:84`) identically. The `git diff` shell-out for `--since` is an adapter concern that belongs in the CLI handler and never touches the query layer — verified there is precedent for workspace-file reads at the composition root (`compose.rs:139 load_store_with_workspace`). **No contamination of the query layer.** ✅

**The blocking gap (REQUEST CHANGES):** RFC-047 §3.2 says `$seeds` is supplied "via `query_with_input` (the existing parameter-binding path)" and uses `WHERE seed.qname IN $seeds`. Two verified problems:
1. `query.rs:35-40` — the `--input` path **is not wired**: `eprintln!("query: --input accepted but not yet wired in v0.1 (Phase A — RFC §6.2)")`. There is no `query_with_input` execution path in the CLI today; only `--params` scalar binding (`query.rs:71 bind_json_params`).
2. `query.rs:104` — `bind_single_param` **rejects arrays**: `serde_json::Value::Array(_) | Object(_) => Err("must be a scalar ... arrays and objects are not supported in v0.1")`. So a **list parameter for `IN $seeds` cannot be bound** through any existing path.

The RFC presents itself as "pure ergonomics, composes existing facts" but it actually depends on a **list-binding capability that does not exist**. This is not a fatal flaw, but it must be made explicit and scoped.

**Amendment that flips to RATIFY:** Add a slice (47-0, before 47-A/B) that lands list-valued param binding — either (a) `impact` constructs the `Query` AST in-process and inserts a `Param::List`/equivalent directly (mirroring `list_callers`' in-process `parsed.params.insert`, *not* going through CLI `--params`), or (b) the RFC drops `IN $seeds` and emits one bound query per seed and unions results in the handler. State which. If (a), confirm `cfdb_core::Param` has (or the slice adds) a list variant — `query.rs:9` imports `Param`; the RFC must verify `Param` is not scalar-only. With the seed-binding path named and confined to the CLI handler (no `cfdb-core`/port change), this is RATIFY.

### RFC-048 — incremental extraction (profile-first)

**48-A (profile): RATIFY.** §3.1 keeps timings out-of-band (stderr/JSON), never in the `G1` graph. Confirmed clean: this is extractor-adapter instrumentation, touches no port. The `EnrichBackend`/`StoreBackend` signatures (`enrich.rs:91`, `store.rs:63`) learn nothing about timers. The deliverable is a measurement, not an abstraction — lowest layer risk in the batch.

**48-B (incremental enrichment): REQUEST CHANGES.** The enrichment passes that would be made incremental (`reachability`, `metrics`, `bounded_context`) are petgraph-adapter modules (`crates/cfdb-petgraph/src/enrich/*`), invoked through thin `impl EnrichBackend` delegates (`enrich_backend.rs:64-194`). Any fingerprint/staleness cache MUST live inside that adapter (a sidecar, per §3.2 "out-of-band sidecar next to the keyspace"), and the seven `EnrichBackend` signatures must stay `fn enrich_*(&mut self, keyspace: &Keyspace) -> Result<EnrichReport, StoreError>` — no cache handle, no fingerprint type, no path in the signature. **Amendment to RATIFY:** the RFC must (1) state the cache lives in the petgraph adapter (or a new `cfdb-incremental` adapter crate), never `cfdb-core`; (2) assert no `EnrichBackend`/`StoreBackend` signature changes; (3) note that incremental reachability/dup/recall are *global* facts (`enrich_backend.rs:151-185` reachability is whole-graph BFS) so the byte-equivalence proof (48-D) is the real gate. Defer to rust-systems on whether 48-B is even feasible under G1 (Q3) — my concern is purely that it not leak infra onto the port.

**48-C (parse-skip): RATIFY** conditional on 048-A justifying it. Fingerprint sidecar is a pure extractor concern.

**48-D (G1 gate): RATIFY.** A CI equivalence script; no layer impact.

### RFC-049 — framework entry-point detectors

**REQUEST CHANGES — the §5 placement question is built on a stale premise.** Verified facts the RFC does not reflect:
- Entry-point emission lives **entirely in `cfdb-hir-extractor`** (`entry_point_emitter.rs` + `entry_point_emitter/{http_route,other_kinds,registers_param,test_bench}.rs`). `cfdb-extractor` (Rust syn) and `cfdb-extractor-php`/`-ts` emit **zero `:EntryPoint`** (grep confirmed: no `EntryPoint`/`entry_point` in the PHP/TS crate `src/`).
- **49-A (clap-derive) is already shipped**: `entry_point_emitter.rs:6` "`cli_command` for `struct`/`enum` with `#[derive(Parser/Subcommand)]`"; `registers_param::has_clap_derive` (`entry_point_emitter.rs:50`). cfdb's own CLI is already `:EntryPoint`s. The RFC's "immediately self-dogfoodable" framing treats this as net-new.
- **49-B (Axum/Actix) is largely already shipped**: `entry_point_emitter.rs:8-19` + `HTTP_ROUTE_METHOD_NAMES` (`:61`) detect axum `Router::route|get|...` and actix `.route(...)`.

So the genuinely-new clean-arch question is **where do the PHP/TS detectors (49-C/49-D) live**, given those crates have no entry-point machinery and `cfdb-hir-extractor` is Rust-HIR-only (it imports `ra_ap_hir`, `entry_point_emitter.rs:34-39` — it cannot host a PHP/TS detector without crossing the language-extractor boundary the BRIEF Q4 forbids).

**Amendment that flips to RATIFY:**
1. Rewrite §3.1/§5 to acknowledge clap + Axum/Actix already exist in `cfdb-hir-extractor`; reframe 49-A/49-B as *recall-hardening + registry-extraction* of existing detection, not new detectors.
2. Resolve the registry home explicitly: the `FrameworkDetector` registry trait is **language-scoped**. A Rust registry can live in/beside `cfdb-hir-extractor` (or a `cfdb-extractor-shared` seam) and own clap/Axum/Actix; a PHP registry lives in `cfdb-extractor-php`; a TS registry in `cfdb-extractor-ts`. The shared *contract* (the `FrameworkDetector` shape + the `:EntryPoint` projection) can live in a shared crate, but **no detector reaches across language-extractor boundaries** (Q4). The RFC must state this split rather than asking the open question.
3. State that 49-C/49-D require **new entry-point-emission capability in the PHP/TS crates** (today they emit none) — that is the real cost and a much larger lift than "register a detector"; it may warrant its own slices/RFC. The "stubs are not arrows" discipline (§3.3) is correctly stated and matches the repo rule.

### RFC-050 — architectural-layer (tier) overlay

**50-A: REQUEST CHANGES — §3.3 prescribes a god-pass.** This is my strongest objection in the batch. RFC-050 §3.3 proposes extending `enrich_bounded_context` to *also* emit `tier`, to dodge the closed-at-7 verb ceiling. Verified against `crates/cfdb-petgraph/src/enrich/bounded_context.rs`:
- That pass has **one documented responsibility**: re-read `.cfdb/concepts/*.toml` and patch `:Item.bounded_context` via `cfdb_concepts::compute_bounded_context` (`bounded_context.rs:1-20`). Lines 22-28 explicitly call it the *single resolution point* for concept ownership — "there is nowhere for [a split-brain] to arise."
- It reads **concept TOML, not `Cargo.toml`** (`bounded_context.rs:61 load_concept_overrides`). It does **not** compute any crate dependency DAG.

Folding tier-DAG topology into this pass adds a **second, orthogonal reason to change** (concept ownership ≠ dependency-graph depth) and a **new infrastructure read** (`Cargo.toml` manifests) into a pass whose whole point is being the one place concept resolution happens. That is an SRP break and a clean-arch layering smell dressed up as OCP.

**Where the `Cargo.toml` read belongs (clean-arch answer to Q1):** Reading manifests is infra and must sit in the petgraph adapter as a **dedicated pass module** — `crates/cfdb-petgraph/src/enrich/tier/run(...)`, structured exactly like the existing per-pass modules and gated through `require_workspace` (the established adapter seam — `enrich_backend.rs:43-61`; the workspace root is attached via `compose.rs:150 with_workspace`). `cfdb-core` stays pure: it declares no manifest type, no DAG type.

**On the verb ceiling (Q2, with solid-architect):** the ceiling is real (`store.rs` doc + `specs/concepts/cfdb-core.md:215` "closed at seven"; `enrich.rs:91-191` is exactly 7). But the clean way to honour it is **NOT** to merge tier logic into `bounded_context::run`. There is a shipped precedent for composing two independent passes behind one verb: `enrich_reachability` runs `reachability::run(All)` then `reachability::run(ProductionOnly)` as two calls in the impl (`enrich_backend.rs:168-174`). By the same shape, if the council insists on no 8th verb, `enrich_bounded_context`'s *impl* can invoke `bounded_context::run` AND a new `tier::run` as two independent adapter passes — the two pass modules stay single-responsibility; only the verb's impl composes them. That is OCP-clean and SRP-clean. **My preference, stated for the council:** because tier is genuinely orthogonal to ownership (RFC §3.4 split-brain test passes — confirmed: `BELONGS_TO` is crate→context, `labels.rs:132`, and there is no tier concept anywhere), the honest move is an **8th verb `enrich_tier`** with explicit council blessing; folding it under a verb named "bounded_context" is a naming lie (screaming-architecture violation — the verb name no longer screams what it does). If the council won't bless an 8th verb, the two-pass-composition fallback is acceptable; merging logic into `bounded_context::run` is not.

**Q1 resolution A vs B (with rust-systems/solid):** clean-arch prefers **A** (enrich-time read, no `DEPENDS_ON` edge) for v1 — it is the smallest schema surface (one `:Crate.tier` attribute) and keeps the manifest read confined to one adapter pass. Materialising a `DEPENDS_ON` crate→crate edge (B) is a genuinely separate capability (and a separate RFC) — confirmed there is **no crate→crate edge today** (`labels.rs:118-160`: `IN_CRATE`, `BELONGS_TO`, `CALLS`, ... no `DEPENDS_ON`). B can come later without invalidating A.

**Amendment that flips 50-A to RATIFY (CONVERGED post-Phase-B — supersedes my Phase-A enrich-pass proposal):** replace §3.1/§3.3 with **resolution C — compute `tier` at EXTRACT time and emit it on the `:Crate` node**, sourced from the `cargo_metadata` graph the extractor *already* loads. Verified: `cargo_metadata` is already a dep of `cfdb-extractor` (`Cargo.toml:29`) and runs via `MetadataCommand::exec()` at extract (`lib.rs:50,156`); `:Crate` nodes are already emitted there (`lib.rs:267-300`); `cargo_metadata::Metadata.resolve` carries the resolved DAG. So `tier` is a pure `Provenance::Extractor` fact (descriptors.rs:26-31 — "walked from syn AST *or `cargo_metadata`*"), like `:Crate.name`.

Why C is *better than* my Phase-A "new `enrich::tier` pass / 8th verb" proposal, and why I converge to it: (a) it sidesteps the verb ceiling entirely — no 8th verb, no composed-pass gymnastics; (b) the `Cargo.toml` read is already in the extractor adapter, so it adds zero new infra and zero second manifest read; (c) `cfdb-core` still declares no DAG/manifest type — only one additive attribute on `:Crate`; (d) determinism is trivially satisfied (same `cargo_metadata` snapshot as every other extract fact). My only non-negotiable from Phase A still holds and is *satisfied* by C: do **not** merge tier into `bounded_context::run`. The G6/G1 wording in §4 is fine for tier (correctly *not* toolchain-scoped — stays inside the dump); but the RFC must **stop citing G6 as a code-level exclusion precedent** (see RFC-052 finding — that precedent is not coded).

**50-B / 50-C: RATIFY** (50-B conditional on 50-A). Pure projection + read-only query.

### RFC-051 — non-code / IaC / DDL

**KEEP-PARKED.** No clean-arch objection to the parked status. The proposed "format-parser plugins behind the extractor-registry seam" (§3) is the right shape *if ever unblocked* — one adapter per format, `cfdb-core` declaring only the new node labels. But it is correctly blocked on (1) no consumer pull (BRIEF house rule 7 — "tool backlog ≠ client chores") and (2) no recall ground-truth. From a layering view there is nothing to ratify yet; un-parking is a charter/consumer decision, not an architecture one. ### RFC-052 — opt-in LLM enrichment

**KEEP-PARKED (never RATIFY) — and the fence the RFC leans on is misdescribed.** Two layers of objection:

1. **Charter (out of architects' hands):** admitting non-determinism is a maintainer decision (RFC §1, BRIEF §1.22). Not ours to ratify.

2. **The G1 fence does not exist as code (verified).** RFC §3.1 claims `summary`/`tags` would be "excluded from the canonical-dump sha256, exactly as `:Item.test_coverage` already is." This is **false at the implementation level**:
   - `canonical_dump.rs:45-160` serializes **every** prop with **no exclusion list** — `props_to_json` (`:131`) maps all props; `node_envelope_json` (`:138`) emits the full props object. There is no per-attribute filter for `test_coverage` or anything else.
   - `crates/cfdb-petgraph/src/enrich/metrics/mod.rs:207` writes `test_coverage` into `props` unconditionally; the `:28` comment "excluded per G6" is **aspirational, not coded**.
   - `ci/determinism-check.sh` hashes the **full** `cfdb dump` output. `test_coverage` is absent from that hash only because the check runs bare `extract` (which never runs `enrich_metrics`) — so the attr is simply *never present*, not *filtered out*.
   
   Consequence: if a consumer runs `enrich_metrics --features llvm-cov` (or, under this RFC, `enrich_summaries`) and *then* `cfdb dump`, the LLM/coverage attributes **WILL** enter the canonical dump and any sha256 over it. RFC-052's "fence" is structural-by-accident, not enforced.

   **The amendment that would make the mechanism sound (IF later blessed):** the first slice must *build* a real per-attribute exclusion filter in `canonical_dump` (a `G6_EXCLUDED_ATTRS` set consulted by `props_to_json`/`node_envelope_json`), prove `test_coverage` and any `EnrichLlm` attr are dropped from the dump, and back-fill the `test_coverage` G6 claim with that same code. Until that filter exists, "excluded from G1, like test_coverage" is an unverified foundation claim (BRIEF house rule 1; memory: *council foundation claims need verification*). On the port: §5's "no model/SDK type in `cfdb-core`" is correct and achievable — the LLM call lives in a petgraph (or new) adapter pass exactly like `git_history`/`metrics`, and `EnrichBackend`'s signature (`enrich.rs:91`) never sees an SDK type.

## Contested-question positions (Q1, Q2, Q3, Q4 engaged)

**Q1 — RFC-050 sourcing (Cargo read vs `DEPENDS_ON` edge). CONVERGED on resolution C.** My Phase-A position was resolution A in a new `crate::enrich::tier` pass; I converge to **resolution C** (extract-time `:Crate.crate_tier`, computed in `cfdb-extractor` where `:Crate` is already emitted — `lib.rs:50,156,193,267-300`). **CORRECTION (ddd-verified, supersedes the "resolved DAG already loaded" claim three of us repeated — including my own follow-up).** The extractor's `MetadataCommand` calls **`.no_deps()`** (`lib.rs:158`), which suppresses `metadata.resolve` → it is `None`. Resolution C still holds on the *where* axis (extract-time, in the extractor adapter); the *how* must be: source intra-workspace tier edges from each `workspace_packages()` entry's declared `[dependencies]` filtered to workspace-member names (cheap, deterministic, no resolution cost) **or** drop `.no_deps()` to populate `metadata.resolve`. The declared-`[dependencies]`-per-package path is preferred. rust-systems' correct amendment still applies: build the DAG from **normal `[dependencies]` only** (exclude dev/build deps) to avoid false cycles. **Outcome: converged with rust-systems, solid, and ddd; ddd's `.no_deps()` catch corrects the shared overstatement.**

**Q2 — verb ceiling. CONVERGED on C-with-no-verb (both my fallbacks dropped).** My Phase-A options were (i) compose tier behind the existing verb's impl, or (ii) a blessed 8th verb `enrich_tier`. Tier must be computed on **every** fresh extract, so it *structurally cannot* live in a verb whose contract is to no-op on fresh extracts — this kills "extend bounded_context" harder than my SRP/naming-lie argument alone. And it makes both my fallbacks *unnecessary*: an 8th verb wouldn't be a god-pass (tier passes split-brain, orthogonal to ownership), just **redundant work for a fact the extractor emits for free**. So the sole clean-arch position is **resolution C — tier at extract time, no verb, ceiling held at 7 by not making it an enrich concern at all**. I endorse solid's Q2 rule (extend a verb only when the new fact shares its input domain + reason-to-change; else prefer extract-time `Provenance::Extractor` → Cypher composition → last-resort honest ceiling raise; never fold an orthogonal concern into a verb body). Port purity + composition root both satisfied. **Converged with solid-architect (Q2 lead).**

### RFC-052 G6 fence — now a 3-of-3 finding (cross-lens contradiction RESOLVED)

**RESOLVED — all three engaged lenses agree the fence is NOT coded.** This was a recorded disagreement (clean-arch + rust-systems vs solid); solid has since read `canonical_dump.rs` directly, confirmed there is no dump-time exclusion, and **corrected their verdict** (table + 052 analysis + summary). It is now a **3-of-3 finding**. The verified facts: `canonical_dump.rs:133-139` (`props_to_json`) iterates `props.iter()` with **no filter**; `node_envelope_json` (`:151-153`) inserts the whole props map; `enrich/metrics/mod.rs:207` writes `test_coverage` unconditionally; the only "G6" is the comment at `enrich/metrics/mod.rs:28` and the spec clause at `cfdb-core.md:209`. `test_coverage` is byte-stable today **only because bare `extract` never populates it** (needs `--features llvm-cov` + `enrich_metrics`, `enrich_backend.rs:212`) — **absent, not filtered**. The fence is *de facto* (populate-or-not), not mechanical.

No remaining disagreement.
