## Per-RFC analysis

### RFC-047 — `cfdb impact` — RATIFY

**SRP of the new dispatch branch (my §5 charge).** The CLI already partitions verbs into four cohesive dispatch families by *kind of work*, not alphabetically: `dispatch_core` (extract/query/violations/check/dump/export), `dispatch_enrich`, `dispatch_typed` (read-only typed query sugar), `dispatch_snapshot` (`crates/cfdb-cli/src/main.rs:104-127`; helpers in `main_dispatch.rs:20/84/190`). `impact` is a read-only typed query view → it belongs in `dispatch_typed`. That keeps each dispatch helper's reason-to-change single (one verb *family* per helper), so adding `impact` does not inflate the SRP of any existing branch.

**The decisive evidence it is not a new responsibility:** `impact` is structurally identical to the already-shipped `list_callers` (`crates/cfdb-cli/src/commands/query.rs:120-137`) — load an embedded `.cypher` template (`LIST_CALLERS_CYPHER = include_str!(".../examples/queries/list-callers.cypher")`, `query.rs:19`), bind a `$param`, execute via `store.execute`, emit JSON. `impact` is the same shape with (a) a multi-seed `$seeds` binding instead of a single `$qname`, and (b) one genuinely new responsibility: `--since` git-diff → changed-file → seed-qname resolution. The query-composition half adds **zero** new abstraction; the doc on `list_callers` even states the typed-verb contract ("one query, many targets, sugar over the raw path", `query.rs:116-119`). Verb-ceiling untouched — confirmed, this is adapter composition, not a `StoreBackend`/`EnrichBackend` method (`specs/concepts/cfdb-core.md:215` blesses exactly this: "New capability extends existing verbs via schema + Cypher composition, not via new trait methods").

**The one open question I was asked (`§5 solid`): should `--since` git-seeding live in `impact` or a shared seed-resolver?** Position: **`impact` only consumer today → keep it local, but extract the *interface* now.** There is no existing git-diff-to-seed resolver in `cfdb-cli` (`grep "git diff|--since|changed_files"` → nothing in `crates/cfdb-cli/src`; the only git shellouts are the *extract* checkout machinery in `commands/extract.rs:246-456`, a different concern). Speculatively building a `SeedResolver` abstraction for a single caller is YAGNI (CRP — don't reuse-couple before there are two reusers). **Amendment (non-blocking, RATIFY stands):** make the resolver a free function `resolve_seeds(SeedSpec) -> Vec<Qname>` with `SeedSpec::{Items(Vec<Qname>), SinceRef(String)}` rather than inlining the two arms in the dispatch match. That is the SRP-correct unit (one reason to change: how seeds are derived) and it is the natural extension point when RFC-047 §6's signature-precise seeding (`signature_hash` diff) lands as a third `SeedSpec` arm — OCP without speculative reuse coupling. This is a code-shape note for the implementer, not a ratification condition.

**Test-surface:** 47-A/B/C blocks are well-formed. One correction in the prescription notes below (47-C ranking is not independently dogfoodable as written).

### RFC-048 — Profile-first incremental — 48-A RATIFY, 48-B REQUEST CHANGES, 48-C/D RATIFY (conditional)

The reframe is SOLID-correct: 48-A ships a *measurement*, which has no abstraction surface and therefore no SOLID exposure, and it gates everything downstream. Right call to make it the only unconditional slice (`RFC-048 §7`).

**48-B (incremental enrichment) — REQUEST CHANGES.** My concern is purely component-principle: the §7 48-B block scopes "reachability / dup / recall recompute to the changed subgraph" but never names *where that module lives* or *what its single responsibility is*. Reachability, dup-clustering, and recall are three separate enrichment concerns today (`enrich_reachability` at `crates/cfdb-petgraph/src/enrich_backend.rs:151`; metrics/dup at `:187`). An "incremental enrichment" module that knows how to incrementally recompute all three is a **CCP violation waiting to happen** — three reasons to change behind one door. **Amendment to flip to RATIFY:** 48-B's §7 must state that incrementality is implemented *per existing enrichment pass* (each pass gains an optional changed-subgraph scope parameter), not as a new cross-cutting "incremental engine" that reaches into all three. The G1-equivalence proof (48-D) then runs per pass. This keeps each pass's SRP intact (one pass = one derived-fact family, incremental or full).

**48-C (parse-skip) / 48-D (G1 gate) — RATIFY conditional on 48-A.** No SOLID objection — the fingerprint sidecar is adapter-local infrastructure (correctly kept out of `cfdb-core` per the RFC §5), and 48-D is a property test, not an abstraction.

### RFC-049 — Framework entry-point detectors — RATIFY

**Verdict moved to REQUEST CHANGES in Phase B (clean-arch surfaced a recreation risk my Phase-A read missed).** The registry is the right OCP *shape*, but it is NOT satisfied by current code, and 49-A/49-B as written would re-implement shipped functionality.

**OCP (my §5 charge) — the registry IS the right open seam, but it is a TARGET state, not the current one.** `FrameworkDetector = { id, languages, present(manifest)->bool, detect(ast,file)->Vec<EntryPoint> }` (`RFC-049 §3.1`) is a textbook OCP polymorphic extension point: adding a framework = adding a `FrameworkDetector` value to a registry, **not** editing a `match`/`const` scan. **But the current Rust detection is exactly that closed scan** (verified): `crates/cfdb-hir-extractor/src/entry_point_emitter.rs:61` `const HTTP_ROUTE_METHOD_NAMES: &[&str] = &["route","get","post",…]` for axum/actix, plus the clap/MCP predicates `has_clap_derive`/`has_tool_attr` imported at `:48-52`. So **clap-derive and axum/actix detection ALREADY ship in `cfdb-hir-extractor`** — RFC-049 49-A ("clap-derive detector") and 49-B ("Axum/Actix detector") as written would *re-implement code that exists today*. That is a DRY/recreation violation (and against the repo's "discover before create" discipline). The OCP claim is only *true after* the existing scan is refactored into the seam.

**Amendments to flip 049 to RATIFY (consolidated with clean-arch):**
1. **Add slice 49-0 (refactor-first):** extract the existing `const`-scan + `has_clap_derive`/`has_tool_attr` predicates (`entry_point_emitter.rs:48-62`) into the `FrameworkDetector` registry seam. Strictly recall-neutral — the same `:EntryPoint`s emitted before and after (a pure structural refactor, `Tests:` = existing recall suite passes byte-identically, no new facts). The OCP extension point is not real until 49-0 lands.
2. **Re-scope 49-A / 49-B** from "implement a clap / axum detector" to "**register the existing** clap / axum-actix detector into the seam introduced by 49-0" — no reimplementation. Their recall fixtures become the seam's regression proof.
3. PHP (49-C) and TS (49-D) are genuinely new (no shipped detector) and consume the seam directly — these stay as drafted.

The `present(manifest)` precondition (§3.1) is the right ISP-flavoured guard: a detector advertises *what it needs to fire* and is inert otherwise, so the registry composes without cross-detector coupling (`RFC-049 §4` negative-fixture invariant makes this checkable).

**ISP amendment (the second flip condition, alongside 49-0 above).** The `detect(ast, file)` signature must take the *language-specific* AST type its `languages` declares, not a unioned super-AST — otherwise every detector depends on a fat interface carrying syn+tree-sitter+tree-sitter-ts shapes it doesn't use (ISP violation, and it forces cross-language-extractor coupling the §5 clean-arch note already forbids). rust-systems owns the concrete mechanism (syn derive-input reading, `§5`); my note is the principle: keep `FrameworkDetector` parameterised/split per language so a Rust detector never sees a PHP AST. I am sending this to rust-systems and clean-arch as the Q4 shared position rather than blocking on it.

**Stubs-are-not-arrows (§3.3)** is honoured and is also the SRP-correct call: an unresolved route is *dropped with a Warning*, not emitted as a `_synthesized` discriminator. A flag like that would be the conflation-of-two-concepts smell the repo bans — good.

### RFC-050 — Layer/tier overlay — REQUEST CHANGES (the verb-ceiling RFC; I lead Q2)

This is the RFC where SOLID does the most work. The schema-bump and crate-DAG facts are verified (BRIEF §4.2: no `crate -[DEPENDS_ON]-> crate` edge; `crates/cfdb-core/src/schema/labels.rs` edge constants confirmed). My objection is to §3.3.

**§3.3 (extend `enrich_bounded_context` to also emit `tier`) is an SRP + CCP violation.** Verified: `enrich_bounded_context` has exactly one reason to read the filesystem today — `.cfdb/concepts/*.toml` (`crates/cfdb-petgraph/src/enrich_backend.rs:118-129`, delegating to `crate::enrich::bounded_context::run(state, &root)`; the `require_workspace` reason string is literally "so the pass can read `.cfdb/concepts/*.toml`"). Making it *also* read `Cargo.toml` manifests and compute topological depth gives it **two unrelated input sources and two reasons to change** (concept-TOML semantics vs. Cargo dependency semantics) — the definition of a god-pass. **Precedent (citation corrected by clean-arch — the scope-narrowing scar at `crates/cfdb-core/src/enrich.rs:157-162` is on `enrich_concepts`, NOT `enrich_bounded_context`; my Phase-A attribution was wrong):** that DDD-Q4 note narrows `enrich_concepts` from a conflated "bounded-context / concept facts" scope to `:Concept` materialisation only, stating verbatim "Context-assignment work was never this pass's responsibility — **`cfdb-extractor` owns it at extraction time**." This is a *stronger* precedent for resolution C than my mis-attributed version: the codebase has already ruled that crate-structure/context work belongs at **extract time**, not in the concept-enrichment verb family. `crate_tier` (another crate-structure fact) belongs at extract time for the identical reason. Re-widening any enrichment verb with this orthogonal concern repeats the exact mistake the codebase already paid to cut back. Contrast the *legitimate* internal decomposition in `enrich_reachability` (`enrich_backend.rs:167-185`): two BFS passes, but **one input domain** (the `CALLS` graph) and **one derived-fact family** (reachability). That is SRP-clean multi-pass; RFC-050 §3.3 is not.

**Decisive reinforcement (surfaced in Phase B with clean-arch): `enrich_bounded_context` is a *re-enrichment* pass that no-ops on fresh extracts.** Its module doc is explicit (`crates/cfdb-petgraph/src/enrich/bounded_context.rs:1-12`): "On a **fresh extraction** this pass is a no-op" — it exists only to patch `:Item.bounded_context` when `.cfdb/concepts/*.toml` changes *between* extractions. `crate_tier`, by contrast, must be computed on **every** fresh extract. Bolting it onto a verb designed to do nothing on a fresh extract is not just an SRP break — it is structurally incoherent. And the same module names the correct pattern: §"Single resolution point (no split-brain)" (`bounded_context.rs:22-28`) — the canonical computation lives at **extract time** (`cfdb_concepts::compute_bounded_context` from the extractor), and enrichment only re-reads/patches via the *same* resolver. That is precisely resolution (C) below: canonical computation at extract time, no new verb.

**But an 8th verb is also wrong** — it breaches the closed-at-7 ceiling (`specs/concepts/cfdb-core.md:215`; `crates/cfdb-core/src/enrich.rs:91` confirmed 7 methods), and the spec is explicit that new capability comes "via schema + Cypher composition, not via new trait methods."

**The SOLID-correct third option the RFC missed — and it flips this to RATIFY.** `tier` is a **pure topological function of the Cargo `[dependencies]` DAG**, and the extractor **already runs `cargo_metadata` and emits `:Crate`**: `crates/cfdb-extractor/src/lib.rs:50` `use cargo_metadata::MetadataCommand;`, the single `exec()` at `lib.rs:156-160`, and `:Crate` nodes emitted from `cargo_metadata::Package` (`lib.rs:267-289`). So `tier` is the same provenance class as every other extractor-walked fact — `Provenance::Extractor` is documented as "Structural fact walked directly from the `syn` AST **or `cargo_metadata`**" (`crates/cfdb-core/src/schema/descriptors.rs:26-31`). **CORRECTION (ddd caught, verified): the *resolved* DAG is NOT in-process today** — the `exec()` sets `.no_deps()` (`lib.rs:158`), so `metadata.resolve` is `None`. My earlier "already loads that DAG / `Metadata.resolve` carries the resolved graph" was wrong. What *is* available under `.no_deps()` is each `Package.dependencies` (the manifest `[dependencies]`); the intra-workspace tier DAG is built by matching those dep names against workspace-member crate names — no resolve, no second `exec()`. **Computing `crate_tier` at extract time on the `:Crate` node, from per-package `[dependencies]`, is:**
- **OCP-correct** — it is "extend via schema, not via new trait method", exactly what `cfdb-core.md:215` blesses.
- **SRP-correct** — no existing verb gains a second reason to change; the extractor's crate-emission already owns "facts derived from `cargo_metadata`", and `crate_tier` is one of those facts.
- **Determinism-correct** — `RFC-050 §4` argues `crate_tier` is a pure topological function and stays inside G1; an extract-time derivation makes that trivially true (it is computed from the same `cargo_metadata` snapshot as the `:Crate` nodes, in one deterministic pass — *given* the per-package-`[dependencies]` sourcing above, not a resolved DAG that does not exist under `.no_deps()`).

**Concrete amendment to flip 050 to RATIFY (consolidated with ddd's Q5 amendments):**
1. Rewrite §3.1/§3.3 to choose **resolution (C): extract-time, on the `:Crate` node, from the `cargo_metadata` resolve graph the extractor already reads.** Drop both "extend `enrich_bounded_context`" (A as written) and any 8th verb.
2. Name the attribute **`crate_tier`** (converged with ddd-specialist — avoids the live `Layer 1/Layer 2` homonym at `crates/cfdb-core/src/schema/descriptors.rs:11-16`; and `crate_`-qualifying it makes the per-crate aggregate boundary explicit, which is exactly why it is one extract-time `:Crate` fact, not a per-item pass).
3. **Kill 50-B (`:Item.layer`)** — converged with ddd from two independent lenses: mine is CRP (it is derived 1:1 via the `IN_CRATE` join, no independent signal — the RFC's own 50-B Target-dogfood row already says "derived 1:1 from 50-A"); ddd's is the aggregate boundary (tier belongs to the `:Crate` aggregate, not each `:Item`). Either way 50-B mints a redundant attribute and is dropped.
4. Keep resolution (B) — materialising a `DEPENDS_ON` edge — explicitly deferred to its own RFC (see Q1 below).
5. **Add an explicit non-goal (from rust-systems, Q1): `crate_tier` is longest-path DEPTH only; 050 does NOT emit instability `I = Ce/(Ca+Ce)` or distance-from-main-sequence D.** Depth (efferent-only) and instability (afferent-vs-efferent, the Zone-of-Pain metric on `cfdb-core`) are different metrics; conflating them is a future split-brain. The Zone-of-Pain metric, if ever pulled by a consumer, is a separate attribute and separate RFC (like `DEPENDS_ON`).
6. **Add a design constraint to §3.2 (from rust-systems, VERIFIED — it qualifies my "one deterministic pass" claim): the tier DAG MUST be built from normal `[dependencies]` only, excluding dev/build deps.** cfdb-self has a real dev-dep back-edge — `cfdb-cli` normal-deps `cfdb-hir-extractor` (`crates/cfdb-cli/Cargo.toml:70`, optional) while `cfdb-hir-extractor` carries a `[dev-dependencies]` edge back to `cfdb-cli` (`crates/cfdb-hir-extractor/Cargo.toml:44,49`). An all-kinds DAG therefore *cycles*, which would false-trip §3.2's "cycle = hard error" gate **on cfdb-self** and make 50-A's self-dogfood (`cfdb-core.crate_tier==0`, `cfdb-cli.crate_tier==max`) unreachable. The deterministic single-pass property holds only with dev/build deps filtered. **Sourcing (ddd's `.no_deps()` correction folded in):** the resolved DAG is not in-process (`lib.rs:158` sets `.no_deps()` → `metadata.resolve` is `None`), so the DAG is built from each `Package.dependencies` filtered to `kind == Normal` AND target ∈ workspace-member names (intra-workspace normal edges only) — not from `Metadata.resolve`. The `kind == Normal` filter does double duty: scopes to manifest deps and removes the dev-dep back-edge that would otherwise cycle on cfdb-self. My §71 "one deterministic pass" bullet is correct *given this filter*; without it, it is false on cfdb-self. **Optional deps are INCLUDED (rust-systems, Q1 close): a feature-gated dependency is still a real dependency edge; excluding it would understate depth. Only `Development`/`Build` kinds are excluded — `Normal` (whether or not `optional`) is in.**

With (C) + `crate_tier` + no 50-B + the normal-deps-only DAG, 050 is a clean single additive-attribute schema bump (`G4`) with the lockstep `graph-specs-rust` fixture PR the RFC already calls for, and `enrich_bounded_context` is left alone.

**Why this also kills the §3.4 split-brain anxiety from the SOLID side:** §3.4 frets that `tier` might belong inside `enrich_bounded_context` because that pass "already derives crate-level structure." It does not — it derives *ownership* (`:Context`), not *depth*. Once `tier` is an extract-time `:Crate` attribute, the two concerns physically live in different code paths (extractor crate-walk vs. concepts enrichment), so there is no resolver to split-brain. (DDD leads §3.4 / Q5; I concur from the component side.)

### RFC-051 — Non-code extraction — KEEP-PARKED

CCP/SRP comment as charged: the proposed per-format parser registry (§3 / §5) is the *right* CCP shape — one vertical slice per format (one node label + edges + recall fixture), each closing over a single format's reason-to-change. That is good component design. It is also why parking is correct rather than killing: the design is sound, only the *trigger* is absent. With no consumer (BRIEF §7 "tool backlog ≠ client chores"; RFC-051 §1.1) and no recall ground-truth (§1.2), filing the largest schema surface in the backlog would be CRP-inverted — building a reusable surface before a single reuser exists. **KEEP-PARKED.** When unblocked, the self-dogfood slice (`.cfdb/queries/*.cypher` as nodes, §7) is the correct CCP-minimal first slice because the rule files are their own ground-truth.

### RFC-052 — LLM enrichment — KEEP-PARKED (never RATIFY)

Per the BRIEF, I do not vote direction. The two mechanism questions I was asked:

**Fold-vs-new-verb (§3.2) — the fold is the defensible SOLID call IF blessed, with one caveat.** A new `enrich_summaries` verb breaches the closed-at-7 ceiling (`cfdb-core.md:215`) — correctly rejected by the draft. The draft prefers folding into an existing verb's internal decomposition (citing the `enrich_metrics` 3-module split). **Caveat:** the only legitimate host is `enrich_metrics`, and even that is a stretch — `enrich_metrics` is "quality-signal facts" (`crates/cfdb-core/src/enrich.rs:181-191`), all *deterministic and recall-adjacent*; a non-deterministic LLM summary is a different reason-to-change. Folding it there to dodge the ceiling would itself be a god-pass (the same SRP mistake I flagged on RFC-050 §3.3). So my SOLID position is sharper than the draft's: **if 052 is ever blessed, the honest move is to argue the closed-at-7 const up to 8 in a reviewed PR (the ceiling is methodology, raisable by argument per `cfdb-core.md:215` "enforced by council review"), NOT to smuggle a non-deterministic concern into a deterministic verb's body.** A fold that violates SRP is worse than an honest, council-blessed ceiling raise.

**The G6 fence — CORRECTION: my Phase-A claim "mechanically real (verified)" was WRONG.** I had cited only the spec (`specs/concepts/cfdb-core.md:209`) and treated the *contract* as if it were *implemented code*. clean-arch and rust-systems both read the dump path and found the opposite — a 2-of-3 finding I now confirm by reading the code myself:
- `crates/cfdb-petgraph/src/canonical_dump.rs` has **no exclusion list**. `props_to_json` (`:133-139`) iterates `props.iter()` and serialises every prop; `node_envelope_json` (`:151-153`) inserts the entire props map. Any prop present on a node — including `test_coverage` — enters the canonical dump and therefore the G1 sha256.
- `enrich_metrics` writes `test_coverage` **unconditionally** when computed (`crates/cfdb-petgraph/src/enrich/metrics/mod.rs:207`); the only "exclusion" is a *comment* at `:28` ("modulo `test_coverage` which is excluded per G6").
- The determinism check passes today **only because bare `cfdb extract` never populates `test_coverage`** — it requires `--features llvm-cov` + the separate `enrich_metrics` verb (`enrich_backend.rs:212`). So the attribute is *absent*, not *filtered*. The "fence" is "the value happens not to be there," not a coded dump-time skip.

**Consequence for 052 (strengthens KEEP-PARKED).** An LLM `summary`/`tags` is, by definition, *populated* (that is the feature). Unlike `test_coverage`, it cannot rely on "happens to be absent." With no coded exclusion filter, a populated `EnrichLlm` attribute would land in the canonical dump and break G1 on the spot. So **"reuse the existing fence" (052 §3.1) is unbuildable as written** — there is nothing to reuse. If 052 were ever blessed, the fence would have to be *built first*: a real prop-name exclusion list in `canonical_dump.rs` (filtering by a `Provenance`/attribute allow-deny set), with a test proving an `EnrichLlm` attribute cannot reach the sha256 — and that fence-build must precede any summary generation (the RFC's own §7 first-slice instinct, now confirmed mandatory and harder than the RFC assumed). `Provenance` is `#[non_exhaustive]` (`crates/cfdb-core/src/schema/descriptors.rs:24`) so adding `EnrichLlm` is additive, but the exclusion mechanism is net-new code, not a reuse. **KEEP-PARKED** — and the maintainer should know the fence is a build, not a free precedent. (Spec-vs-code reconciliation flagged to the lead; recorded by clean-arch as a 2-of-3 finding, now 3-of-3 with my confirmation.)

## Contested-question positions (Q1, Q2, Q4)

### Q2 (I LEAD) — the verb ceiling. RULE delivered.

**Rule:** *Extend an existing `enrich_*` verb only when the new fact shares that verb's single input domain and reason-to-change. If it introduces a second input source or a second provenance class, it is a god-pass — do not extend. Prefer, in order: (1) compute it at extract time as a `Provenance::Extractor` schema attribute if it is a pure function of data the extractor already loads; (2) compose it via Cypher over existing facts (no new fact at all); (3) only if neither works and a genuinely new derived-fact family exists, argue the closed-at-7 const up to 8 in a reviewed council PR. Never fold an orthogonal concern into an existing verb's body to dodge the ceiling — an SRP violation is a worse outcome than an honest, argued ceiling raise.*

Applied: RFC-050 `tier` → path (1), extract-time, because `cargo_metadata` is already loaded (`crates/cfdb-extractor/src/lib.rs:50`). RFC-052 `summary`/`tags` → if ever blessed, path (3), an honest ceiling raise — **not** the §3.2 fold, which would be a god-pass on `enrich_metrics`.

**Phase B with clean-arch (Q2 peer):** sent the rule + resolution (C) and explicitly invited challenge ("push back if you think bounded-context-enrichment is the right home"). At report time clean-arch's reply had not landed (all four lenses still in Phase A). Recorded as **proposed-converged, awaiting peer ack** — the extract-time resolution is constructed to satisfy clean-arch's stated charge (it keeps `Cargo.toml`-reading in the extractor adapter where it already is, out of any enrichment port, and leaves `EnrichBackend` at 7), so I expect convergence; if clean-arch disagrees the lead has the divergence for R2 synthesis.

### Q1 — RFC-050 sourcing: A (enrich-time attribute) vs B (materialise `DEPENDS_ON` edge). SDP/SAP analysis.

**SDP (Stable-Dependencies) / SAP (Stable-Abstractions) of materialising the crate DAG as edges (B):** materialising `DEPENDS_ON` does **not** change cfdb's *own* crate stability metrics — it adds *data in the graph cfdb produces*, not a dependency in cfdb's source. So the SDP/SAP-of-cfdb argument is neutral on B. The real cost of B is component-principle of a different kind: a new edge label is a permanent addition to the *stable abstraction* that is `cfdb-core`'s schema vocabulary (`crates/cfdb-core/src/schema/labels.rs`), which sits in the Zone of Pain (maximally stable, maximally concrete — every keyspace and `graph-specs-rust` depends on it). Adding `DEPENDS_ON` there is a high-cost, hard-to-revert commitment (SAP says stable things must be abstract/additive-only; an edge label is concrete and forever). **Position: neither A-as-written nor B — resolution (C) (extract-time attribute), and B is its own RFC.** B's *only* incremental value over the `tier` attribute is "who depends on crate X" queries, which has **no named consumer** (same bar that parks 051) — so pulling the edge in now is CRP-inverted. **B is a separate RFC, deferred** (RFC-050 §6 already lists it as deferred; I confirm that is correct and add: it should not be folded back in by the council).
