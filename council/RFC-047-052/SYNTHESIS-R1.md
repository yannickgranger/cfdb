## The five load-bearing findings (each verified by ≥2 lenses or the lead)

1. **RFC-047's seed-binding path does not exist** (clean-arch, lead-verified). The RFC composes `query_with_input` to bind `WHERE seed.qname IN $seeds`, but `--input` is an unwired stub (`crates/cfdb-cli/src/commands/query.rs:39` prints "accepted but not yet wired in v0.1") and `bind_single_param` rejects arrays (`query.rs:104` — "arrays and objects are not supported in v0.1"). **List-valued param binding has no path today.** → 047 needs a seed-binding slice before 47-A/B.

2. **RFC-048 mis-models the `extract` pipeline** (rust-systems, endorsed by clean-arch). `cfdb extract` (`crates/cfdb-cli/src/commands/extract.rs:42-110`) runs only `cargo metadata` + `syn` walk + deferred-resolve + ingest + optional `--hir` load + save. It runs **no enrich pass and no recall** — `enrich_reachability`/`enrich_metrics`/`dup_cluster_id` are separate `cfdb enrich-*` verbs (`crates/cfdb-petgraph/src/enrich_backend.rs:151,187`) and recall is the separate `cfdb-recall` crate (`ground_truth.rs:118`). The RFC's entire "where extract's seconds go" premise (both original and reframe) named phases that aren't in `extract`. → 48-A's profiled phase list must be corrected; 48-B/C re-derived per-pass from it.

3. **RFC-049's first two slices are already shipped** (clean-arch + rust-systems, lead-verified). `crates/cfdb-hir-extractor/src/entry_point_emitter.rs` already detects clap (`cli_command`, `#[derive(Parser/Subcommand)]`), MCP (`mcp_tool`), **axum + actix** (`http_route`, `HTTP_ROUTE_METHOD_NAMES:61`, issues #124/#125), cron, and websocket. The detection is **HIR-side** (needs `Semantics`/`sema.to_def` qname resolution — `entry_point_emitter.rs:291-299`), not syn-side as RFC-049 §3.2 claims. → 49-A/B reframe to "generalize existing HIR detectors into the registry, byte-identical"; only 49-C/D (PHP/TS) are green-field, and those need new `:EntryPoint` emission in crates that emit none today.

4. **RFC-050's A-vs-B dichotomy is false; resolution C dominates** (unanimous after Phase B). `tier` is a pure topological function of the Cargo `[dependencies]` DAG — a structural fact in the same class as `:Crate` itself — so it is emitted at **extract time** as `Provenance::Extractor` on the `:Crate` node, co-located with the existing `:Crate`/`:Context`/`BELONGS_TO` emission (`crates/cfdb-extractor/src/lib.rs:267-289`). This sidesteps the verb ceiling entirely (no 8th verb, no extending `enrich_bounded_context` — which reads only `.cfdb/concepts/*.toml` and would become a god-pass). Naming: **`crate_tier`** not `layer`/`tier` (live "Layer 1/Layer 2" homonym, `descriptors.rs:11-16`). **50-B (`:Item.layer`) killed** (two independent lenses: solid CRP, ddd aggregate-boundary — `IN_CRATE` already joins items to the crate tier).

5. **RFC-052's G1 fence is unbuilt, not pre-existing** (clean-arch + rust-systems, lead-noted; resolves the one cross-lens contradiction). `crates/cfdb-petgraph/src/canonical_dump.rs:45-139` has **no exclusion list** — it serializes every prop. G6/`test_coverage` holds today *only because the attribute is never populated by default* (`enrich/metrics/mod.rs` default `coverage_json: None`; the self-dogfood test says the exclusion is "observed trivially"). An LLM `summary` is populated by definition → it **would** enter the canonical dump and break G1. solid-architect read the *spec contract* (`specs/concepts/cfdb-core.md:209`, which documents the G6 intent) and called the fence "mechanically real"; clean-arch + rust-systems read the *implementation* and found no coded filter. **Lead adjudication: the code reading is authoritative — the fence is a documented contract with no enforcing code.** If 052 is ever blessed, its first slice must *build* a `const G1_EXCLUDED_ATTRS` filter in `canonical_dump` (a `const` in source per `CLAUDE.md §6 rule 8`, never an allowlist file), not "reuse" a fence that does not exist.

## Contested-question resolutions

- **Q1 (RFC-050 sourcing) — RESOLVED: resolution C.** Not A (enrich-time, a god-pass on `enrich_bounded_context`) and not B (a forever `DEPENDS_ON` edge label in cfdb-core's Zone-of-Pain schema with no consumer — deferred to its own RFC). Extract-time `:Crate.crate_tier`. DAG sourced per-package from `Cargo.toml [dependencies]`, **normal deps only** (`.no_deps()` stays — see Lead verification 2), workspace-filtered. Longest-path depth; `cfdb-core` = tier 0; normal-deps cycle = hard error.
- **Q2 (verb ceiling) — RESOLVED + rule recorded.** solid's rule: *extend an existing `enrich_*` verb only when the new fact shares its single input domain + reason-to-change; else prefer (1) extract-time `Provenance::Extractor` attribute, (2) Cypher composition, (3) an honest council ceiling-raise to 8 — never fold an orthogonal concern into a verb body to dodge the ceiling.* Applied: RFC-050 → path (1), question dissolves. RFC-052 (if ever blessed) → path (3), an honest raise, NOT the §3.2 fold into `enrich_metrics` (that would be a god-pass).
- **Q3 (RFC-048 feasibility) — RESOLVED.** 48-A profile is the right unconditional first slice but must measure the real phases (finding 2). Incremental enrichment is determinism-feasible (all three passes use `BTreeSet`/`BTreeMap` + stable sort, so a byte-identical merge is possible) but value-unproven and mis-bundled; 48-B is rejected as written and re-derived per-pass from the corrected profile. If recall (a separate gate, not extract) is the real pain, "cache the rustdoc JSON" is the higher-value separate RFC (RFC-048 §6 already names it). The fingerprint/cache is a build mechanism, never vocabulary (ddd) and never on a port signature (clean-arch).
- **Q4 (RFC-049 registry placement) — RESOLVED.** The `FrameworkDetector` registry IS the OCP seam (registration, not match-arm edit — solid). The shared *contract* may live in `cfdb-lang`; each *impl* lives in its language-extractor crate, parameterised by the language-specific AST (ISP — solid), and no detector reaches across language-extractor boundaries (clean-arch; the orphan rule enforces it anyway). Rust detectors that resolve handler qnames are **HIR-side** (finding 3). clap-derive reads the derive *input* token text, never macro-expanded output (rust-systems, Q4) — the §5 "macro-expanded" worry is moot.
- **Q5 (DDD concept ownership) — RESOLVED: split-brain test passes.** `tier` ⟂ `:Context`: `:Context` is ownership via crate-name prefix stripping with zero DAG knowledge (`overlay.rs:32-49`); `tier` is Cargo-DAG depth. They are independently variable (`cfdb-core` tier-0 and `cfdb-cli` tier-3 share one context — `studies/003 §2`). No existing "tier" resolver (grep clean). CREATE justified, as `:Crate.crate_tier`. "framework" (RFC-049) is extraction-time provenance, not a concept cfdb owns — the deferred `:EntryPoint.framework` attribute is the right call. `:Item.tags` (RFC-052, if ever) must stay distinct from the deterministic `:Concept` overlay — no alias.
