## 1. Problem

`keel-harness#2.2` places a verdict instrument's positive controls in the instrument's own tree and CI. The consumer's `bin/gates.sh` carries 32 legs (23 `text`, 8 `instrument`, 1 `php`) and re-proves them on every pull request. Each `text` leg that asks a question about code is a `grep` standing in for a fact the graph does not hold. This RFC settles the fact model those rules need, and nothing else.

The measurement, on the consumer at its pinned SHA: 7771 nodes and 10406 edges. Node labels present: `:Crate` 1, `:Module` 79, `:Item` 1967, `:CallSite` 5724. Edge labels present: `IN_CRATE` 1967, `IN_MODULE` 1967, `INVOKES_AT` 5724, `CALLS` 676, `IMPLEMENTS` 72. Absent entirely: `:Argument`, `:Literal`, `:File`, `:Param`, `:Field`, `HAS_ARG`, and any fact for a PHP attribute.

**Global function calls are seen.** `classify_call` handles `function_call_expression` (`crates/cfdb-extractor-php/src/call_walker.rs:76`); `callee_path` is the name as written and `resolve_target` is import-resolved. `date`, `time`, `microtime`, `random_int`, `random_bytes` are rows today.

**Constructions are not seen.** `object_creation_expression` is not an arm of `classify_call` (`call_walker.rs:68-98`: `function_call_expression`, `scoped_call_expression`, `member_call_expression | nullsafe_member_call_expression`, `_ => None`). Ground truth on the consumer: 167 `new X(` under `src/` + `tests/`, of which 71 are `new DateTime(Immutable)?(` and 58 sit under `Domain/` or `Application/`. cfdb rows: 0.

**Arguments are not seen in any PHP shape.** `:Argument` and `HAS_ARG` are emitted by `cfdb-extractor` (`src/call_visitor.rs:125-142`) and `cfdb-hir-extractor` only. The PHP emitter writes `caller_qname`, `callee_path`, `callee_last_segment`, `kind`, `file`, `line`, `is_test`, `resolver`, `callee_resolved` and nothing else (`crates/cfdb-extractor-php/src/emitter.rs:92-101`).

**Imports are built and thrown away.** `crates/cfdb-extractor-php/src/imports.rs` collects a per-file `ImportTable` (`collect`, `:33`) covering plain clauses, aliases and `namespace_use_group` (`absorb_declaration`, `:52-55`), deliberately skipping `use function` and `use const` (`imports_a_symbol_not_a_class`, `:44`). The table is consumed only to resolve callee and implements targets (`ImportTable::resolve`, `:11`), and no fact reaches the graph. 1540 `^use ` lines in the consumer's tree, 0 rows.

**String literals are not seen.** `:Literal` is Rust-only (`crates/cfdb-extractor/src/literal_visitor.rs`, `syn::Lit::Str`). 5 `http(s)://` literals and 147 locale-shaped literals in the consumer's tree, 0 rows.

**Attributes are not seen at all** — no label, no property. 68 `#[...]` lines, 13 of them `#[AsAlias(Port::class)]`, 0 `#[Autowire]`.

### 1.1 What the one existing rule can and cannot see

`.cfdb/queries/arch-ban-nondeterminism-in-domain.cypher` on the consumer matches `:CallSite` where `caller_qname =~ '^App\\[A-Za-z]+\\Domain\\.*'` and `callee_path =~ '.*(Uuid::v[0-9]|random_bytes|random_int|bin2hex|uniqid|microtime|mt_rand)$'` and the file is not under `tests/`. Three shapes were planted in one throwaway workspace and the rule was run over the extract:

| planted in `App\Catalogue\Domain` | `:CallSite` emitted | rule fires |
|---|---|---|
| `Uuid::v4()` | yes, `callee_path` `Uuid::v4` | **yes** — 1 violation; the rule's positive control holds, it is armed and not vacuous |
| `date('Y-m-d')` | yes, `callee_path` `date` | no — the alternation lists no `date` and no `time` |
| `new \DateTimeImmutable('now')` | **no** — the file yielded 3 call sites, none for the construction | no |

The second row is a rule gap on the consumer, not an index gap: adding `date|time` to the alternation makes it fire against today's keyspace, with no cfdb change. The third row is this RFC.

### 1.2 Why the construction alone is not enough

The consumer's clock leg (`no_clock_outside_adapter`, grounded `coreen-domaine-pur#9`) reads `new \\?DateTime(Immutable)?\((['\"]now['\"])?\)`. It fires on an empty argument list or on `'now'`, and **not** on `new DateTimeImmutable('2024-01-01')`. The discriminator is argument 0. A rule built on the construction alone would be **coarser than the bash it replaces** — it would refuse a fixed-date construction the leg admits. §2.2 without §2.3 is a regression dressed as progress, which is why they are one RFC and not two.

### 1.3 What the tests tree already offers, and the one attribute that lied

`walk_dir` skips only `vendor/` (`crates/cfdb-extractor-php/src/lib.rs:73`), so `tests/` is indexed: 4785 of 5724 call sites and 1251 of 1967 items carry a `tests/` file. A rule reaches the tests tree with `file =~ '^tests/.*'`, and every rule in this RFC does so.

At the pin, `is_test` was hard-coded `false` on every PHP call site (`emitter.rs:99`): 5724 of 5724 `false`, including all 4785 under `tests/`. The TypeScript producer does the same at three sites (`crates/cfdb-extractor-ts/src/{emit.rs:202,methods.rs:93,call_walker.rs:75}`). That is a defect in an existing attribute, not a missing fact type; it was filed as cfdb #685 and the PHP half is fixed independently of this RFC. **I7 stands regardless**: no rule in this RFC's lineage fences on `is_test`, because the TypeScript half is still a constant and the invariant should not depend on which producer filled the attribute.

## 2. Scope

### 2.1 Use statements as facts

Ships a `:File` node per PHP source file and one `:Import` node per class-importing `use` clause, owned by its file through a new `HAS_IMPORT` edge, each `:Import` carrying the imported name's fully-qualified form as a **string, whether or not that name is a node in the graph** (§3.1). `use function` and `use const` clauses emit nothing, matching what `imports_a_symbol_not_a_class` already excludes.

**Named consumers, and exactly what this clause serves of each.** The council measured every leg rather than taking §2.1's first draft at its word, and the honest table is narrower than "five legs retired":

| leg (`bin/gates.sh`) | grounding | what it actually reads | served by `:Import` |
|---|---|---|---|
| `seam_no_framework` | `coreen-architecture#7` | `^use (Symfony\|Doctrine\|Stripe\|Helio)\` | **fully** — the whole pattern is an import question |
| `domain_no_framework` | `coreen-domaine-pur#1` | a SIX-name anchored alternation (`Symfony\|Doctrine\|Stripe\|Helio\|Psr\|Twig`, two more than `seam_no_framework`) **or** an inline `\Symfony\…` anywhere on a line | **half** — the inline-FQN alternative is a name reference with no `use` clause, which no import fact can see |
| `no_adapter_in_domain_test` | `coreen-domaine-pur#7` | unanchored `KernelTestCase`, `Doctrine\`, `Stripe\`, `HttpFoundation` over whole files | **partial** — a PSR-4 file normally also imports what it extends, but `extends KernelTestCase` is a `base_clause` and no fact here reaches it; and `HttpFoundation` is a mid-FQN segment, so a rule must use contains-semantics, not a prefix |
| `no_adapter_in_seam_test` | `coreen-architecture#7` | the same plus `WebTestCase` | **partial**, same reason |
| `adapter_names_live_in_four_places` | `coreen-hexagones#14` | adapter basenames word-grepped over whole files, with an admission carve-out reading `^[[:space:]]+use ([A-Za-z]+Contract);` | **not at all** — see §6 |

Retiring a leg is the consumer's judgment on its own evidence, not this RFC's promise. What this clause promises is one leg fully expressible, one half, two narrowed.

### 2.2 `object_creation_expression` as a call site

Ships a fourth arm on `classify_call` so that `new X(...)` emits a `:CallSite` with `kind` `"new"` (§3.2). Named consumers: `no_clock_outside_adapter` (`coreen-domaine-pur#9`) and the `new DateTime` half of `domain_no_nondeterminism` (`coreen-domaine-pur#2`). Closes the 71 invisible `DateTime` constructions and the 58 constructions under `Domain/` or `Application/` measured in §1.

### 2.3 `:Argument` on PHP call sites

Ships `:Argument` nodes and `HAS_ARG` edges from the PHP producer, for every call site it emits — including the construction of §2.2 — reusing cfdb-043's node-id formula, position semantics and closed `kind` set unchanged (§3.3, §3.4). Named consumer: the clock-read discriminator of §1.2. This clause unblocks no leg on its own; it is what keeps §2.2's rule as precise as the leg it retires.

### 2.4 Does not ship

Everything in §6. In particular: no attribute fact, no PHP `:Literal`, no `SchemaVersion` bump, no change to any Rust or TypeScript emission, no `extends` fact, and no convergence of `source_text` across producers.

## 3. Design

### 3.1 `:File` and `:Import` for PHP

#### 3.1.1 The file node

`:File` already exists in the vocabulary (`crates/cfdb-core/src/schema/labels.rs:14`) with a descriptor at `crates/cfdb-core/src/schema/describe/nodes/structural.rs:57-84` declaring `crate`, `loc`, `module_qpath`, `path`.

The descriptor is wrong today and this clause corrects it rather than widening a falsehood. **No producer emits `loc` or `module_qpath` on a `:File`** — the only occurrence of `"loc"` under `crates/` is the descriptor itself (`structural.rs:65`). The Rust file walker emits `path`, `crate` and `is_test` (`crates/cfdb-extractor/src/file_walker.rs:71-81`), and `is_test` is not declared at all. So the real Rust-versus-PHP attribute delta is one attribute, `is_test`, not the two the first draft claimed.

The PHP producer emits, per file it walks, `:File` with id `file:php-workspace:{workspace-relative path}` — the shape `file:{crate}:{rel_path}` the Rust walker uses (`file_walker.rs:70`), with the PHP producer's single synthetic crate (`CRATE_ID` `crate:php-workspace`, `lib.rs:15`) as the crate segment. Attributes: `path` (workspace-relative, the normalization `:Item.file` already uses through `cfdb_lang::workspace_relative`) and `crate` (`php-workspace`). Not `loc`, not `module_qpath`: nobody measures them and an attribute emitted empty is worse than one absent.

**No `IN_CRATE` edge, and no `IN_MODULE` edge.** The first draft proposed `IN_CRATE`; the council established that the Rust `:File` carries no such edge (its only edge is the conditional `IN_MODULE` at `file_walker.rs:82-91`; every `EdgeLabel::IN_CRATE` in `cfdb-extractor` is item-scoped — `item_visitor/visits.rs:333`, `item_visitor/emit/mod.rs:189,243`). A PHP-only `IN_CRATE` would make `MATCH (f:File)-[:IN_CRATE]->(:Crate)` silently return PHP files only, and it would carry zero information besides: the PHP producer has exactly one synthetic crate, so every PHP `:File` would point at the same node. `IN_MODULE` is likewise omitted — a PHP file may open several namespaces, so file-to-module is not the function the Rust walker's edge asserts.

**Id formulas are hoisted, not duplicated.** `crates/cfdb-core/src/qname/node_id.rs` exports nine constructors — `item_node_id`, `item_node_id_for_target`, `matchsite_node_id`, `callsite_node_id`, `entrypoint_node_id`, `param_node_id`, `field_node_id`, `variant_node_id`, `argument_node_id` — and **no `file_node_id`**, so `file:{crate}:{rel_path}` is written by hand at `file_walker.rs:70`. Writing it a second time in a second crate is the drift `argument_node_id` exists to prevent, and §3.3 routes the `:Argument` id through the shared constructor in the same RFC. `file_node_id(crate: &str, rel_path: &str) -> String` moves to `cfdb_core::qname`, and `import_node_id(file: &str, fqn: &str, idx: usize) -> String` joins it there rather than being hand-built in the producer — otherwise this one slice would hoist one formula and hand-roll another. Both producers call `file_node_id`. Dependency-neutral: `cfdb-core` is already a dependency of both.

A shared label rather than a `:PhpFile` is the established practice here, not an innovation: the PHP producer already shares `:Module` while emitting a disjoint attribute set (`lib.rs:141-150` emits `name` and `path`; the descriptor at `structural.rs:28-55` declares `crate`, `file`, `is_inline`, `qpath` — zero overlap). Splitting the label would also freeze the hand-duplicated id formula into two vocabularies.

#### 3.1.2 The import node

One `:Import` node per class-importing `use` clause, id `import:{file path}:{fqn}:{idx}`, built by `cfdb_core::qname::import_node_id` (§3.1.1), where *idx* is the zero-based count of prior clauses in the same file importing the same FQN. The per-key-ordinal shape is the one `callsite_node_id` already carries (`crates/cfdb-core/src/qname/node_id.rs:63-65`, `callsite:{caller_identity}:{callee_path}:{local_idx}`) — noting that the PHP producer hand-builds that same string at `call_walker.rs:45-53` instead of calling the core constructor, which is the bypass §6 records as a chore.

**The ordinal is load-bearing, and the RFC's first draft contradicted itself over it.** That draft excluded the alias from the id, reasoning that "an alias never changes the identity of what is imported" — and then prescribed a fixture whose five class-importing clauses (`use A\B\C;`, `use A\B\C as D;`, `use A\{B, C as E};`, `use \A\B;`) yield the FQNs `A\B\C`, `A\B\C`, `A\B`, `A\C`, `A\B`, asserted four nodes, and produced three distinct ids under its own formula. Three numbers for one fixture, and no execution needed to see it. Putting the alias in the id does not cure it either: `use \A\B;` and the group's `B` both lack an `as` (`imports.rs:100` trims the leading backslash), so both carry an absent alias and still collide.

The runtime consequence is the second beat, and it is worse than a double-count. `Emitter::emit_node` pushes both nodes (`emitter.rs:47-52`), but ingest is last-write-wins — `PetGraph::ingest_one_node` finds the existing index by id and overwrites it (`crates/cfdb-petgraph/src/graph.rs:64-81`) — so **one import is silently dropped, not duplicated**. On every leg in §2.1, each of which is a ban, an under-count is a false negative: the gate passes while the banned import sits in the source. And cfdb's RFC-054 identity-contention warning, built for exactly this, **cannot fire on this class**: `classify_reingest` returns `Silent` when both nodes carry an equal `file` prop (`crates/cfdb-petgraph/src/ingest_contention.rs:15-22`), and every `:Import` collision is same-file by construction, since the id embeds the file and §3.1.2 denormalises `file` onto the node. Which clause survives is deterministic but semantically arbitrary — colliding imports have equal `Node::sort_key` (`crates/cfdb-core/src/fact.rs:134-136`), the stable sort preserves source order, and the last-declared clause wins.

Attributes:

- `fqn` — the fully-qualified imported name with no leading backslash, as `absorb_clause` computes it (`imports.rs:78-107`: group prefix joined, leading `\` trimmed). This is the string the legs read. **It is emitted whether or not a node with that name exists in the graph**, which is the point: every framework name the legs hunt lives in `vendor/`, which `walk_dir` skips, so a model that only records resolved targets records nothing the legs asked for.
- `alias` — the `as` name **as written**, absent when the clause carries none. Note that `ImportTable` is not a source for this: `insert` keys on `alias.to_ascii_lowercase()` (`imports.rs:28-30`), so the table holds a case-folded name and no line number. Both must be newly retained; "exactly as `absorb_clause` already computes it" is true of the FQN and of nothing else.
- `file` — workspace-relative path, denormalized onto the node the way `:CallSite.file` (`emitter.rs:97`) and `:Item.file` already are, so a leg fences on `^src/[A-Za-z]+/Domain/` or `^tests/` in one `MATCH` with no hop.
- `line` — 1-indexed line of the clause.

`HAS_IMPORT` — new edge label, from `:File` to `:Import`, no attributes. It is the `HAS_*` shape the vocabulary already uses (`HAS_FIELD`, `HAS_VARIANT`, `HAS_PARAM`, `HAS_ARG`, `HAS_CONST_TABLE`): owner to a constituent of the owner's own declaration, with the constituent carrying a denormalized back-reference. A verb-shaped `IMPORTS` would have been wrong — `CALLS`, `IMPLEMENTS` and `RETURNS` all denote a *resolved* relation between two real items, which §3.1.3 refuses.

**`:Import` is not the `ImportTable`.** The table is a lossy, case-folded, last-write-wins alias-to-FQN resolution map built to answer "what does this written name resolve to"; `:Import` is the lossless record of each declaration. `count(:Import) ≥ |ImportTable|`, strictly on real files.

#### 3.1.3 Why not the alternatives

- **An attribute on `:Item`.** Rejected: an import is not a property of a class, and a two-class file duplicates it. The duplicate is not inert — `adapter_names_live_in_four_places` counts naming sites.
- **A JSON blob property on `:File` holding the whole import list.** Rejected: `PropValue` is scalar-only (`crates/cfdb-core/src/fact.rs:10-16` — `Str`, `Int`, `Float`, `Bool`, `Null`), so the list would be a `Str` and every leg would become a regex over a serialized array. That is a grep with extra steps, which is the thing this RFC is retiring.
- **An `IMPORTS` edge `:Item` → `:Item`, emitted only when the target resolves.** Rejected: it loses precisely the imports the legs hunt, since a vendor name is never a node. Synthesizing a flagged stub for the absent target is the shape that conflates two types and re-splits them with a discriminator; the import declaration is a real fact and is modelled as one (I6).

#### 3.1.4 What the walk did not reach

The walker of §3.1.1 visits the roots `composer.json` declares and nothing else (cfdb #687). That is correct — the project's own declaration is what says where its code lives — and it leaves the keyspace silent about everything outside those roots. A reader cannot tell a project with no PHP outside its declared roots from one carrying a thousand files there, and silence reads as absence.

Measured on the consumer's tree, the omission is not a rounding error and its shape changes with the tree's state. At a clean checkout of `31f9c71`: 33 files, `config/` 15, `migrations/` 11, and seven at the repository root or under `public/`, `deploy/` and `assets/`. On a built worktree of the same project, excluding `vendor/`: 1636, of which **1606 are the generated `var/`** — the compiled container, the proxies, the cache. So on a working tree roughly 98 % of what is not walked is machine-written and the hand-written remainder is configuration and migrations.

**The fact.** The PHP producer emits `undeclared_php_file_count` on its `:Crate` — an `int`, the number of files whose name ends `.php` that lie under the workspace root and under no declared root, with `vendor/` excluded. One attribute, one node, no new label and no new edge.

`vendor/` is excluded because it is composer's install target, third-party code the project did not author and never declares; counting it would put the figure in the tens of thousands and answer a question nobody asked. The existing walk already skips a directory named `vendor` for the same reason.

**Why the crate carries it.** The producer emits exactly one `:Crate` (`CRATE_ID`, `lib.rs`), which is the node standing for the walked workspace, and an extraction-wide figure belongs on it. A producer-specific attribute on a shared label is the established shape in this vocabulary rather than an innovation: `:Item` carries `php_construct`, `ts_construct` and `language`, and `:Crate` carries `language` from the TypeScript producer alone and `published_language` from two producers of three. Four of those five were emitted for releases before anyone declared them and reach the descriptor through cfdb #693, which is where the precedent is written down; the shape is old, its statement is new.

This is **not** the shape §3.1.1 refused for `IN_CRATE`. That refusal turned on a shared *edge*: `MATCH (f:File)-[:IN_CRATE]->(:Crate)` looks language-neutral and would have answered for PHP alone. An attribute absent on another producer's node answers null, which is what every producer-specific attribute in the vocabulary already does, and no query is silently narrowed by it.

**Why not a `:File` per file the walk skipped.** The producer never read those files, so no fact hangs off such a node, and a `:File` distinguished only by a flag is exactly the synthesized-stub shape §3.1.3 refuses for an unresolved import target — a discriminator standing in for a type that was never split. It would also change `count(:File)` under every rule that counts files, which is a silent change to a term already in use.

**Why not a note rather than a fact.** `LanguageProducer::produce` returns `(Vec<Node>, Vec<Edge>)` and nothing else. A note means either a library writing to stderr, which the port does not contract for, or widening the port for all four producers — a larger change than the thing it would carry, with no second caller asking for it.

**Cost and determinism.** The count requires traversing the workspace outside the declared roots, which §3.1.1's walker does not do; the traversal reads directory entries and parses nothing. The result is a count over a set of paths, so I1 holds unchanged: two runs over an unchanged tree produce the same number. I2 holds too: an added optional attribute is a non-breaking addition under cfdb `CLAUDE.md` §5, `SchemaVersion::CURRENT` stays `V0_8_0`, and no `graph-specs-rust` lockstep is due. A keyspace extracted before this slice carries no such attribute, which reads as absent and not as zero — a distinction a rule counting on the number must respect, since zero is a real answer meaning the project declares every file it holds.


### 3.2 The construction call site

A fourth arm on `classify_call` (`call_walker.rs:68`), matching `"object_creation_expression"` and returning the constructed class as written together with its import-resolved constructor.

**`object_creation_expression` carries no fields.** `node-types.json` for the pinned grammar gives it `"fields": {}`, unlike `function_call_expression`, whose `function` and `arguments` children are field-named. `child_by_field_name("function")`, `("class")` and `("arguments")` all return `None`. §3.2 therefore cannot follow the field-based discipline of the `scoped_call_expression` arm: both the class node and the `arguments` node are found by iterating children and matching kinds.

- `callee_path` — the class name as written in source (`\DateTimeImmutable`, `DateTimeImmutable`, `Uuid`), so a rule reads what a developer would grep for. Same discipline as `classify_scoped_call` (`call_walker.rs:101-126`), which puts the written scope in `callee_path` and the resolved name in `resolve_target`.
- `callee_last_segment` — as today, via `callee_last_segment` (`emitter.rs:23`).
- `kind` — `"new"`, the **fourth** member of `:CallSite.kind`. The set today is `call`, `fn_ptr` and `serde_default` (`crates/cfdb-core/src/schema/describe/nodes/call_graph.rs:16`); `fn_ptr` and `serde_default` are Rust-only shapes emitted by `cfdb-extractor` (`call_visitor.rs:55,71` and `item_visitor/visits.rs:202`), and `serde_default` is read across a crate boundary at `crates/cfdb-enrich/src/attr_call_resolution.rs:8`, so it is a live contract and not a narrative line. The descriptor is **extended, never narrowed**. Every PHP call site carries `call` today (5724 of 5724 measured), which is the range of the producer and not of the label.
- `resolve_target` — `{resolved FQN}::__construct`, through `ImportTable::resolve`. A construction calls a constructor; when the class is in the graph and declares one, `callee_resolved` is true and a `CALLS` edge lands on the constructor item exactly as it does for `scoped_call_expression`. When the class declares no explicit constructor, or lives in `vendor/`, `callee_resolved` is `false` and the call site stands alone — the honest reading, and the one every rule in §2.2 uses. A `CALLS` edge to the class's own `:Item` was considered and rejected: a PHP class `:Item` carries `kind` `"trait"` (`lib.rs:167-170`), and a `CALLS` whose target is a type rather than a callable is a second meaning for one edge label.

**Which class positions emit a call site.** A call site is emitted only when the first named child is `name` or `qualified_name`. `anonymous_class` (`new class { }`), `variable_name` (`new $cls()`), `dynamic_variable_name`, `parenthesized_expression` (`new ($f->t())()`), `subscript_expression`, `member_access_expression`, `nullsafe_member_access_expression` and `scoped_property_access_expression` emit nothing — the same silence `_ => None` gives every unhandled shape today. `callee_path` holds a name as written; a variable is not a name, and giving it one would be a second meaning for the attribute.

**`new self()`, `new static()` and `new parent()` parse as a plain `name` child** with that text — **not** as `relative_scope`, which appears only under `scoped_call_expression` and `class_constant_access_expression`. They route through the relative-scope handling `classify_scoped_call` already has (`call_walker.rs:101-126`): `self` and `static` resolve to `{enclosing_class_qname}::__construct`, `parent` is unresolved. Without this they resolve through `qualify(current_ns, "self")` (`imports.rs:24`) to `App\…\self`, a qname that can never match.

**Reconciliation with cfdb-041's `kind` ruling.** cfdb-041 refused a `kind` attribute on `:Literal` as a three-way homonym against `:Item.kind` and `:ConstTable.element_type` (`crates/cfdb-core/src/schema/describe/nodes/overlay.rs:121`, enforced at `crates/cfdb-core/src/schema/describe/tests.rs:252-256`). That ruling governs adding a `kind` *axis to a new label*. `"new"` adds a *member to an existing label's existing enum*, whose axis — the syntactic form that produced this call fact — already carries `call`, `fn_ptr` (a path passed as a function pointer, not an invocation at all) and `serde_default` (a callable named inside an attribute). A construction is a point on that same axis. No second meaning is created and the two rulings do not conflict. A `:Construction` label or an `is_construction` boolean would fragment a well-formed enum across two attributes for no gain.

### 3.3 `:Argument` on PHP call sites

`:Argument` and `HAS_ARG` are cfdb-043's, and this clause adds a producer, not a vocabulary. Node id through `cfdb_core::qname::argument_node_id(callsite_id, position)` (`crates/cfdb-core/src/qname/node_id.rs:88`) — unchanged formula `arg:{callsite_id}#{position}`; `#` cannot occur in a PHP identifier or namespace, so the separator stays unambiguous. Attributes, matching the descriptor at `crates/cfdb-core/src/schema/describe/nodes/call_graph.rs:38-105`: `col`, `file`, `kind`, `line`, `position`, `source_text`.

**One `:Argument` per `argument` node.** The pinned grammar wraps every argument: `f('s')` parses as `(arguments (argument (string)))`, and `argument`'s own fields carry a named argument's label (`name`) and a by-reference `&` (`reference_modifier`). The unit of "an argument" is therefore the wrapper, not the expression, and §3.3 and §3.4 are both written against it.

- `position` — zero-indexed, and **position 0 is the receiver for `member_call_expression` and `nullsafe_member_call_expression`**, the first positional argument for `function_call_expression`, `scoped_call_expression` and the construction of §3.2. That is cfdb-043's rule for `ExprMethodCall` versus `ExprCall`, carried across unchanged so `cfdb_core::schema::labels::RECEIVER_POSITION` means one thing in every producer. Positions are assigned by enumerating the `arguments` node's `argument` children **before any text is extracted**, so an extraction failure can never renumber a later argument while the determinism gate stays green.
- `source_text` — the verbatim source bytes of the **`argument` node**, taken from its byte range through the existing `text` helper (`crates/cfdb-extractor-php/src/lib.rs:337`) **and copied to an owned `String` at visit time**, since `text` returns a borrow of the source buffer that does not outlive `walk_file`. The wrapper's range, not the expression child's: for an ordinary argument the two are identical (`'now'` is bytes 137..142 under both, so §1.2's clock discriminator is unaffected), and for a named argument, a spread or a by-reference argument the wrapper is what carries `name:`, `...` and `&`. There are **two** normalisations in play, not three: rowan source text (`cfdb-hir-extractor`, `crates/cfdb-hir-extractor/src/call_site_emitter/facts.rs:140`) and a tree-sitter byte range are both byte-faithful, and `cfdb-extractor`'s `expr.to_token_stream().to_string()` (`crates/cfdb-extractor/src/call_visitor.rs:129`) is the lone re-print. **This RFC introduces no new normalisation — PHP joins the existing majority and the syn producer is the outlier.** The divergence is pre-existing and undeclared: the descriptor names `proc-macro2` as the sole mechanism while claiming both producers, so it is already false for the HIR producer today, in a monolingual Rust keyspace, with no PHP involved. See I8 and §6.
- `col` — 1-indexed column from the tree-sitter start position. `tree_sitter::Point::column` is a **byte** offset within the line, where the Rust producer's `col` is a `proc_macro2` **char** offset (`call_visitor.rs:139`). On any line containing non-ASCII the two disagree, and the consumer carries 147 locale-shaped literals, so this is not hypothetical. The descriptor states the divergence.
- Named arguments (`f(name: $x)`), spreads (`f(...$xs)`) and by-reference arguments (`f(&$x)`) carry a position like any other; what distinguishes them is inside `source_text` and, for `kind`, in §3.4's rules.

**Extraction is eager, and this is the load-bearing implementation constraint.** `walk_file` owns both `source` (`lib.rs:85`) and `tree` (`lib.rs:94`) as locals and returns at `:101`, dropping both, while `resolve_pending_call_sites` runs at `lib.rs:52` after the whole file loop at `:46-49`. By the time any `:CallSite` node is constructed, every tree-sitter node and every source byte for that file is gone. `source_text`, `kind`, `position`, `line` and `col` are therefore extracted inside `visit` (`call_walker.rs:32-66`), where the node is alive, and carried as **owned** values on `PendingCallSite`; `source_text`'s byte-exactness holds only because the slice is copied to a `String` at visit time. The receiver for `member_call_expression` and `nullsafe_member_call_expression` is read at the same site through `node.child_by_field_name("object")` — it is discarded today (`call_walker.rs:93-96` returns `(name, None)`), so receiver capture is new work in this clause, needing no change to `classify_call`'s return type.

### 3.4 The argument-kind vocabulary is one closed set

`kind` is cfdb-043's closed set — `path`, `method_call`, `call`, `ref`, `literal`, `other`. The classifier operates on the `argument` **wrapper**, in three steps, in order:

1. If the `argument` carries a `reference_modifier` field (`f(&$x)`), the kind is `ref`. This is a field, not a node kind — no node kind distinguishes a by-reference argument.
2. Otherwise let *expr* be the `argument`'s single named child that is neither its `name` field (the label of a named argument) nor its `reference_modifier`. If *expr* is `variadic_unpacking` (`f(...$xs)`), descend to its child.
3. Classify *expr*'s node kind:

| tree-sitter node kind of *expr* | `kind` |
|---|---|
| `string`, `encapsed_string`, `heredoc`, `nowdoc`, `integer`, `float`, `boolean`, `null` | `literal` |
| `variable_name`, `name`, `qualified_name`, `member_access_expression`, `nullsafe_member_access_expression`, `scoped_property_access_expression`, `class_constant_access_expression` | `path` |
| `member_call_expression`, `nullsafe_member_call_expression`, `scoped_call_expression` | `method_call` |
| `function_call_expression`, `object_creation_expression` | `call` |
| anything else | `other` |

A double-quoted string is `encapsed_string` whether or not it interpolates; only single-quoted is `string`. `Foo::class` is `class_constant_access_expression`, hence `path`. `reference_assignment_expression` (`$a = &$b`) is an assignment, never an argument, and is deliberately absent from the table; if it ever appears as one it falls to `other`, which is correct.

A `variadic_placeholder` — the first-class-callable `f(...)` — is a direct child of `arguments` and is **not** wrapped in an `argument`. It is skipped: it denotes a reference to a function, not an argument, and emitting one would shift every subsequent position.

Every node kind named above was verified present in `node-types.json` for `tree-sitter-php 0.23.11`, the version pinned through `crates/cfdb-extractor-php/Cargo.toml`, and observed in a parse against that grammar.

**Getting the level wrong is not a cosmetic error.** A classifier written against `arguments`' children rather than the `argument` wrapper maps every PHP argument to `other` — and cfdb-043 §4 Invariant 10, which this clause carries forward verbatim and which is test-enforced at `call_graph.rs:70-74`, forbids a ban rule from fencing on `kind='other'`. §2.3 would then ship a fact type no rule is permitted to read.

**The set centralises; the match does not.** `cfdb_extractor_shared::classify_arg_kind` takes a `syn::Expr` (`crates/cfdb-extractor-shared/src/lib.rs:2`) and cannot be reused; nor can `cfdb-hir-extractor`'s independent copy at `crates/cfdb-hir-extractor/src/call_site_emitter/facts.rs:117-126` — so the duplication is already three-way before PHP, and the correct PHP signature is `fn(tree_sitter::Node) -> &'static str`, which no shared crate can host without making the PHP grammar a transitive dependency of the default Rust-only build. The mapping is per-producer by necessity and stays so.

What is shared is promoted from prose to code. This RFC adds to `crates/cfdb-core/src/schema/labels.rs`, beside `RECEIVER_POSITION`, six named `pub const &'static str` for the kind values and a `pub const ARG_KINDS: &[&str]` listing them, following the `G1_EXCLUDED_ATTRS` idiom at `crates/cfdb-core/src/fact.rs:87-91`. Each producer keeps its own `match` and returns one of the consts, so I5's "a PHP-only member is a defect" fails to compile rather than failing a test someone must remember to write, and §7.3's test asserts the PHP mapping's range against `ARG_KINDS` rather than against a doc string.

**No dependency-permission change and no new crate-dependency edge.** The PHP producer names the consts directly — it already depends on `cfdb-core` (`crates/cfdb-extractor-php/Cargo.toml:42`), as does `cfdb-hir-extractor` (`:22`). The one crate that could not name them is `cfdb-extractor-shared`, which `.cfdb/workspace-dep-rules.toml` forbids from depending on `cfdb-core`; it keeps its string literals and loses nothing it has today, and RFC-060 never touches it. Recorded and deliberately not requested: that shim is 52 lines with one `pub` item and one consumer, and the justification written beside its dep-rule — that `cfdb-hir-extractor` would share it — is falsified, since HIR depends on `cfdb-core` and wrote its own copy of the match; folding it into `cfdb-extractor` would let the syn classifier name the consts and would delete the section rather than loosen it. That is a chore unit under cfdb `CLAUDE.md` §1, and no lens conditioned ratification on it.

## 4. Invariants

- **I1 — Determinism.** Two `cfdb extract --features lang-php` runs over an unchanged tree produce byte-identical keyspaces. Every new node id is derived from a workspace-relative path plus a source-order position, and `produce_facts` sorts nodes and edges by `sort_key` (`crates/cfdb-extractor-php/src/lib.rs:55-56`) after `Emitter::finish` returns them unsorted (`emitter.rs:123-125`). Determinism alone does not prove correctness here: §3.1.2's rejected id formula was byte-stable *while dropping nodes*, which is why the ordinal is an invariant and not a convenience.
- **I2 — No `SchemaVersion` bump.** `:Import` and `HAS_IMPORT` are new labels; `:File` and `:Argument` gain a producer. Per cfdb `CLAUDE.md` §5 these are non-breaking additions that MAY keep the version; `SchemaVersion::CURRENT` stays `V0_8_0` (`crates/cfdb-core/src/schema/version.rs:115`), and no lockstep `graph-specs-rust` fixture PR is required. `cfdb-core` carries no `[features]` block, so `cfdb schema describe` advertises the two new labels on a default build that cannot produce them — the same asymmetry `:Argument` already carries behind `hir`. `cfdb extract` output on a non-PHP tree is unaffected, which is what §7's self-dogfood sha256 asserts.
- **I3 — Nothing an existing keyspace holds changes.** No Rust or TypeScript emission is touched. The `:File` and `:CallSite.kind` and `:Argument` descriptor edits this RFC prescribes are corrections and extensions; no declared value is removed.
- **I4 — Cross-dogfood stays at zero.** `ci/cross-dogfood.sh:46` runs **cfdb's own** `examples/queries/arch-ban-*.cypher` corpus — 10 rules at the pin, not the companion's — plus the `self-enrich-deprecation` pass (`ci/cross-dogfood.sh:59-80`), against `graph-specs-rust` at its pinned SHA. `graph-specs-rust` is a Rust workspace with no `composer.json` at its root, so `PhpProducer::detect` (`lib.rs:25`) is false and the PHP producer emits nothing there: no node this RFC adds can reach any of the 11 gate surfaces. (The first draft named six rules that do not exist; the corrected inventory was verified by running the script.)
- **I5 — One vocabulary across languages.** `RECEIVER_POSITION` means position 0 is the receiver in every producer that emits `:Argument`; the `kind` set is closed and shared; `argument_node_id` is the one id formula. A PHP-only member of any of the three is a defect, not an extension.
- **I6 — An import fact never invents a node.** A `:Import` records a name; it never creates an `:Item` for an unresolved target and never carries a synthesized or external discriminator.
- **I7 — No rule in this RFC's lineage fences on `:CallSite.is_test`.** Rules fence on `file`. The PHP half of the constant was fixed under cfdb #685, but the TypeScript producer still asserts `false` at three sites, so the invariant does not depend on which producer filled the attribute.
- **I8 — `source_text` is producer-normalised and NOT comparable across producers.** Two normalisations exist: byte-faithful — `cfdb-hir-extractor`'s rowan source text (`call_site_emitter/facts.rs:140`) and the PHP producer's tree-sitter byte range — against `cfdb-extractor`'s re-printed `proc-macro2` token stream (`call_visitor.rs:129`), which is the lone outlier. The descriptor names only the re-print while claiming both existing producers (`call_graph.rs:42-44` against `:93-102`), so it is false today for a producer it already names, in a monolingual Rust keyspace. A Cypher rule matching `source_text` is single-producer by construction and MUST fence on `:CallSite.resolver`. `RECEIVER_POSITION`, the `kind` set and `argument_node_id` (I5) are the three terms that DO mean one thing everywhere; `source_text` is deliberately not a fourth.

## 6. Non-goals

- **The trait `use` and the closure `use`.** PHP spells three unrelated constructs with one keyword: the namespace import (`namespace_use_declaration`), the trait use inside a class body (`use_declaration`, a child of `declaration_list`), and the closure capture (`anonymous_function_use_clause`). `:Import` records the first only. `coreen-hexagones#14` is a naming-site clause, not an import clause — `adapter_names_live_in_four_places` reads the trait `use` (leading-whitespace anchored, 55 such lines in the consumer's tree) and word-greps type names over whole files; no fact in this RFC reaches it, and it is named here so a later reader does not mistake `:Import` for the fact that retires it.
- **An `extends` fact.** `base_clause` is not read by the producer (`lib.rs:196` captures `class_interface_clause` only), so `extends KernelTestCase` is invisible. It is what the two `*_test` legs read on their non-`use` lines, and it is not shipped here.
- **PHP attributes.** `#[AsAlias]`, `#[Autowire]` and the other 68 attribute lines get no fact. Rationale: there is no wiring leg among the 32 today, so this would unblock a leg that does not exist. Counts recorded so a later RFC starts from a measurement: 68 `#[...]` lines, 13 `#[AsAlias(Port::class)]`, 0 `#[Autowire]`.
- **PHP string literals.** `:Literal` stays Rust-only. No leg among the 32 reads PHP literals — `free_text_only_in_privacy` reads Doctrine XML mappings. 5 `http(s)://` literals, 147 locale-shaped literals.
- **`use function` and `use const` clauses.** Excluded from §2.1, matching `imports_a_symbol_not_a_class` (`imports.rs:44`). A purity rule that wants to ban `use function Symfony\…` reopens this deliberately, with its own consumer named.
- **Converging `source_text` on one normalisation.** Two normalisations exist and the descriptor documents only the outlier (I8). Converging means bringing `crates/cfdb-extractor/src/call_visitor.rs:129` onto the byte-faithful majority — which I3 forbids here, and which is not a one-liner: `syn::Expr` carries no source bytes, so byte-exactness on the syn side means re-reading the file and slicing by `span()`, with its own determinism and recall surface. Filed as its own unit; this RFC documents the divergence rather than inheriting it silently.
- **The PHP producer's bypass of `callsite_node_id`.** `crates/cfdb-core/src/qname/node_id.rs:63-65` already builds `callsite:{caller_identity}:{callee_path}:{local_idx}`, and `call_walker.rs:45-53` hand-builds the byte-identical string instead of calling it. Pre-existing, produces no wrong fact, and out of scope here — but recorded, because §3.1.1's argument for one owner per id formula is only coherent if the exception is named.
- **`:CallSite.is_test` on the TypeScript producer.** The PHP half was fixed under cfdb #685; `emit.rs:202`, `methods.rs:93` and `call_walker.rs:75` still assert `false`. Its own unit.
- **Method-call dispatch resolution.** `$x->m()` still yields a bare `callee_path` with no owning class. Unchanged and long-standing; no consumer has asked.
- **A `RESOLVES_TO` edge from `:Import` to `:Item`.** Nothing in the legs needs it, and `CALLS` and `IMPLEMENTS` already carry resolved usage.
- **A per-directory breakdown of what the walk did not reach.** `PropValue` is scalar-only, so a breakdown is one node per undeclared directory and a new label — more machinery than the question has earned, and no consumer has asked which directories. §3.1.4's count is what makes the omission questionable, and the walked set is fully enumerable as `:File`, so a reader reconciles the number against their own `find` without cfdb modelling the answer. Recorded with its measurement so a later RFC starts from one: on the consumer's built tree the 1636 files divide as `var/` 1606, `config/` 15, `migrations/` 8, and seven elsewhere.
- **The TypeScript producer's equivalent of §3.1.4.** `cfdb-extractor-ts` decides what to walk its own way, and this RFC does not touch it. Symmetry there is its own unit with its own measurement; prescribing it here would be writing against a walk nobody has measured, which is the error §1 exists to avoid.
- **A `kind` member for array literals.** §3.4's table is faithful to cfdb-043's closed set and `array_creation_expression` is not in it, so a PHP array literal classifies `other` — and cfdb-043 §4 Invariant 10 forbids a ban rule from fencing on `other`. Measured on the consumer's tree at the 060-C extract: of 705 `other` arguments, **212 are array literals**, the largest single shape in that bucket, ahead of 77 binary or concatenated expressions and 69 closures. So no rule can say "constructed with a literal configuration array" today, and the reason is the vocabulary rather than the producer. Widening the set is a cross-producer change — the syn and HIR classifiers own the same six members — and belongs to its own round with a consumer named, not to a PHP slice.
- **A dependency fence for `cfdb-extractor-php`.** Seven crates carry no section in `.cfdb/workspace-dep-rules.toml` — `cfdb-extractor-php`, `cfdb-extractor-ts`, `cfdb-lang`, `cfdb-hir-extractor`, `cfdb-hir-petgraph-adapter`, `cfdb-concepts`, `cfdb-cli` — and of the nine sections that are declared, the one without an enforcing `tests/architecture_dep_rule.rs` is `[cfdb-extractor-shared]`. Both are pre-existing and systemic. RFC-060 adds no dependency to any crate, so fencing one of the seven here is scope this RFC did not earn; filed as a chore unit under cfdb `CLAUDE.md` §1, filed rather than dropped.

### 7.4 Ordering and the merge bar

060-A stands alone; its file-level overlap with the other two is only the descriptor module and `specs/concepts/`. 060-C depends on 060-B in that it must also cover the construction's arguments. 060-B without 060-C would support a rule strictly coarser than the leg it aims at (§1.2), so the consumer should not write a rule against `kind='new'` until 060-C has landed. **That is a recommendation to the consumer, not an invariant of this RFC**: the rule file lives in `cours-coreen/.cfdb/queries/`, no cfdb gate reads it (`ci/cross-dogfood.sh:8` pins the companion to `yg/graph-specs-rust`), and cfdb acquires no mechanism to enforce it without depending on its own client. What cfdb owns is the ordering of its own slices, which is stated above.

Each slice's acceptance bar is cfdb `CLAUDE.md` §3 unchanged: the self-hosted ban rules, extractor recall, determinism and cross-dogfood gates all green, and no baseline, ceiling or allowlist file introduced for any of them.
